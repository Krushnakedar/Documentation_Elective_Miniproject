01 · Abstract

CloudBox is an educational secure-file-storage and content-delivery prototype. It explains client-side file segmentation, AES-256-GCM authenticated encryption, private Amazon S3 storage, and CloudFront delivery as connected but distinct concerns. The project is a learning artifact, not a managed storage product or audited security system.

The prototype is intentionally small so that each step of the workflow can be inspected in isolation: a file is split into ordered blocks, every block is encrypted and authenticated with its own initialization vector, the resulting package is stored as an ordinary static object, and delivery happens over HTTPS through a CDN in front of a non-public origin. Nothing in the chain depends on a hidden server component, which means the behavior of the demo can be verified with browser developer tools.

The documentation also spends time on what is not present. There is no identity provider, no upload API, no key escrow service, and no cloud automation. Those omissions are not oversights — they are the parts of a production storage system where most of the real security engineering lives, and the project deliberately names them instead of implying they are solved.

Client-side processing

Segmentation and encryption happen in the visitor's browser through the Web Crypto API.

Private origin

Object storage is described as non-public, with access limited to a distribution identity.

Static delivery

Pages and packages are served as static assets — no backend, no database, no session layer.

Honest scope

Educational artifact only. No audit, no penetration test, no production guarantee.

02 · Introduction

Large-file workflows involve transport, storage, confidentiality, integrity, and retrieval. CloudBox makes those concepts visible through a static educational site and a browser-oriented file workflow. It separates the trust decisions made by the client from the access rules of a cloud origin.

A useful way to read this document is to follow a single file through the system. The file is chosen locally, so the endpoint holds the plaintext first. It is divided into blocks, so the processing cost is bounded and can be reasoned about one unit at a time. Each block is encrypted and tagged, so confidentiality and integrity travel together. The encrypted package is then treated as an opaque blob that any static host can serve, and the key is handled as a separate secret outside that channel.

That separation — package versus key, client versus origin, origin versus edge — is the core teaching point. Most misunderstandings about "secure cloud storage" come from collapsing these boundaries into a single word like "encrypted" and assuming every boundary is covered by the same mechanism.

Trust boundaries in the prototype

  • Browser endpoint: sees plaintext, holds the key in memory, and performs all cryptography. A compromised endpoint defeats the model.
  • Network transport: protected by HTTPS/TLS. This protects bytes in flight, not bytes at rest or bytes already decrypted.
  • Object storage origin: holds only ciphertext packages when configured as intended; access is restricted to the distribution.
  • CDN edge: caches and forwards static content. It is a delivery accelerator, not an authorization service.
  • Recipient: must obtain the key through a separate channel. The package alone is not enough to read the file.

03 · Problem statement

Users often confuse HTTPS, private buckets, and encryption at rest with end-to-end file confidentiality. They are not interchangeable. The project demonstrates where file bytes are transformed and where origin access is controlled, while making missing services and assumptions explicit.

Three specific confusions motivate the design:

  • "It has a padlock, so the file is private." A TLS padlock says the connection to a specific endpoint is encrypted. It says nothing about who can read the file later, or who controls the endpoint that receives the plaintext.
  • "The bucket is private, so the data is safe." Bucket policies control who can retrieve an object. They do not change the object's contents. A private bucket full of plaintext is still a plaintext store — it is only harder to reach.
  • "Encryption at rest is end-to-end encryption." Encryption at rest protects media against physical or infrastructure-level exposure. It does not prevent the storage service, or anyone holding its keys, from reading the object.

CloudBox answers these confusions by making the transformation happen visibly on the client, by keeping the key out of the stored package, and by describing the cloud portion strictly as an access and delivery pattern. The demo can therefore show a file whose ciphertext is publicly retrievable yet whose plaintext is not recoverable without a separately held key.

What each mechanism actually protects
Mechanism Protects against Does not protect against
HTTPS / TLS Eavesdropping and tampering in transit Anyone who can read the file at either endpoint
Private bucket + OAC Unauthorized direct object retrieval Content exposure if the object is readable downstream
Encryption at rest Media theft and infrastructure-level access Service operators with key access; plaintext at the client
AES-GCM in the client Confidentiality and tamper detection of stored bytes A compromised browser, extension, or device

04 · Objectives

The project has four concrete objectives. Each one is written so that it can be checked by inspecting the site or the browser workflow rather than by trusting a claim.

  • Demonstrate block-based file processing with a configurable block size. The interface shows how a file of size S becomes ceil(S / B) blocks, how the final block may be short, and how block size affects memory behavior.
  • Explain AES-GCM confidentiality and tamper detection at a high level. The documentation avoids inventing cryptography and instead points at the Web Crypto primitives, explaining the role of the key, the IV, and the authentication tag.
  • Show private S3 and CloudFront OAC as a static content delivery pattern. The architecture pages describe a non-public origin, a distribution that signs origin requests, and the policy conditions that make that work.
  • Provide a transparent test ledger and useful operational documentation. Manual test cases are listed with expected results, and the troubleshooting section maps symptoms to plausible causes.

Non-objectives

CloudBox explicitly does not aim to be a file-sharing product, a backup service, a key management system, or a reference implementation of AWS best practice. Where a real deployment would require a service, the documentation names the service and stops short of pretending it exists.

06 · Technology stack

The presentation layer uses semantic HTML, CSS, and vanilla JavaScript. Vite is a development and build tool that emits a static multi-page distribution. The architecture discussion references browser cryptography concepts, Amazon S3, CloudFront, Origin Access Control, and HTTPS.

No backend or database is required for this educational website. Test annotations can be saved locally in the visitor's browser.

Stack by layer
Layer Technology Purpose
Markup Semantic HTML5 Accessible page structure, landmarks, and headings
Styling CSS with theme tokens Light/dark themes, responsive layout, print-friendly reading
Behavior Vanilla JavaScript (ES modules) Theme toggle, mobile navigation, copy buttons, local test notes
Cryptography Web Crypto API AES-GCM encryption, decryption, and random IV generation
Build Vite (via pnpm workspace filter) Dev server and static multi-page output
Delivery (described) S3 + CloudFront + OAC Private origin with edge caching and signed origin requests

Why no framework

The site intentionally avoids a component framework. The content is mostly long-form reading and a handful of interactions, so a small amount of hand-written JavaScript keeps the output inspectable and the build trivial. It also keeps the security discussion honest: a reader can view source and see every script the page loads.

Why no backend

A backend would introduce sessions, credentials, and a server that sees plaintext — three large topics that would compete with the actual subject of the project. By staying static, CloudBox keeps the focus on client-side transformation and origin access control.

07 · Hardware and software requirements

Hardware

  • A computer or phone with enough free memory for browser-based file processing; large files need substantially more memory than their source size.
  • Internet access is needed only for hosted pages or configured CloudFront downloads.

Runtime software

  • A modern browser with JavaScript and Web Crypto enabled.
  • A secure context such as HTTPS or localhost for cryptographic APIs.
  • Local file access granted by the user through a file picker.

Build software

Node.js and pnpm are needed only to develop or build the static pages.

Memory reality check

A browser demo typically holds the original file, the working block, the ciphertext block, and the serialized package in memory at once. A 200 MB file can therefore require well over half a gigabyte of transient allocations. Prefer smaller files when demonstrating the flow.

09 · Local setup

From the workspace root in Replit, run the artifact workflow or use the command below. In Windows PowerShell, open the project workspace folder first and run the same pnpm command. To deploy the static site, build it and upload the contents of the output directory. 

# Replit or Windows PowerShell, from the workspace root
pnpm --filter @workspace/cloudbox run dev

# Build static files for S3 / CloudFront
pnpm --filter @workspace/cloudbox run build
# output: artifacts/cloudbox/dist/

Web Crypto is restricted outside secure contexts in many browsers. Use HTTPS in Replit or localhost for local development rather than opening an HTML file directly from disk. No database setup is required.

Suggested walkthrough

  1. Start the dev server and open the printed local URL.
  2. Confirm the theme toggle persists after a page reload.
  3. Open the security lab and confirm the crypto controls are enabled.
  4. Select a small file, run the workflow, and inspect the package output.
  5. Reconstruct the file and compare its size and checksum with the original.
  6. Resize the window or open dev tools to verify the responsive navigation.

Common setup problems

  • Opening the HTML file directly from disk: the page loads, but crypto.subtle may be unavailable. Use the dev server instead.
  • Running pnpm from the wrong folder: the workspace filter must be resolved from the workspace root.
  • Stale assets after a build: rebuild and hard refresh, or clear the CDN cache in a hosted environment.
  • Relative paths when hosting in a subpath: keep the built folder intact; do not flatten css/ and js/.

10 · Segmentation

The source file is treated as a byte sequence and split into ordered ranges. A block size of 1 MiB is a practical educational default, not a universally optimal setting. The final block may be smaller than the configured size.

For a file of size S bytes and block size B, estimated block count is ceil(S / B). Empty files need explicit format handling.

Worked examples
File size Block size Blocks Final block
1 KiB 1 MiB 1 1 KiB
5 MiB 1 MiB 5 1 MiB (full)
5 MiB + 1 byte 1 MiB 6 1 byte
0 bytes 1 MiB 0 or 1 Requires explicit rule

Choosing a block size

Block size is a trade-off between per-block overhead and peak memory. Smaller blocks mean more IVs, more Base64 strings, and a larger JSON envelope, but each individual operation stays small. Larger blocks reduce metadata overhead but require bigger contiguous allocations and produce coarser progress reporting.

  • Smaller blocks (e.g. 64–256 KiB): smoother progress, lower peak memory per step, more metadata.
  • 1 MiB: a readable default for demos; easy to reason about and still small enough for phones.
  • Larger blocks (e.g. 8 MiB): fewer chunks, but higher memory pressure and longer per-block stalls.
Determinism note

Segmentation is deterministic given a size and block size, but encryption is not: fresh random IVs mean the same file produces a different package each time. Do not use package bytes as a content hash.

11 · Cryptography

CloudBox uses an extractable 256-bit AES key for the demonstration, with AES-GCM and a 128-bit authentication tag. It generates a fresh random 12-byte IV for each block. AES-GCM combines encryption with an authentication tag that detects ciphertext changes; a robust design must never reuse an IV with the same key and must reject any block that fails authentication.

Cryptographic APIs should use the browser's Web Crypto implementation rather than custom algorithms. This educational prototype does not claim independent cryptographic review.

The three inputs that matter

Key

256 bits of AES key material. Held in memory for the demo and downloaded separately from the package — never bundled with it.

IV / nonce

12 random bytes per block. The pair (key, IV) must never repeat. Random generation makes collisions negligible at demo scale.

Authentication tag

128 bits appended to each ciphertext. Any modification to the block causes decryption to fail loudly rather than silently produce garbage.

Rules the demo follows

  • Use Web Crypto; never implement AES or GCM by hand.
  • Generate a new IV for every block; never derive it from the index alone.
  • Store the IV alongside the block, not as a global constant.
  • Treat authentication failure as a hard stop, not a warning.
  • Keep the key out of URLs, logs, localStorage, and repositories.

Rules a production system would still need

  • Key wrapping, rotation, revocation, and recovery procedures.
  • Non-extractable keys where the workflow allows it.
  • Streaming encryption so plaintext never fully resides in memory.
  • Interoperable test vectors and cross-implementation verification.
  • Independent review of the package format and its metadata.
Terminology

"Extractable" means the browser will hand the raw key bytes back to JavaScript. That is convenient for a demo that must download a key file, and unsuitable for real protection against a compromised page.

12 · Package format

The versioned package records the original file name and type, file size, block size, count, and indexed chunks. Each chunk carries a Base64 IV and authenticated ciphertext. The raw key is kept out of the package and downloaded separately. 

{
  "format": "cloudbox-encrypted-package",
  "version": 1,
  "algorithm": "AES-256-GCM",
  "originalName": "example.bin",
  "originalType": "application/octet-stream",
  "originalSize": 42,
  "blockSize": 1048576,
  "blockCount": 1,
  "chunks": [
    { "index": 0, "iv": "Base64-encoded 12-byte IV", "ciphertext": "Base64-encoded ciphertext and GCM tag" }
  ]
}

Validate package sizes and schema before allocating memory. Do not trust a supplied filename as a filesystem path. The example values and payload strings are illustrative, not an actual encrypted package.

Field reference
Field Type Validation
format string Must equal the documented identifier
version integer Reject unknown major versions
algorithm string Must match the supported cipher suite
originalName string Display only; sanitize before any file write
originalType string Advisory MIME type; do not execute or auto-render
originalSize integer Cross-check against decrypted byte total
blockSize integer Positive, within an allowed range
blockCount integer Must equal chunks.length
chunks[].index integer Contiguous, unique, ascending from zero
chunks[].iv Base64 Decodes to exactly 12 bytes
chunks[].ciphertext Base64 Longer than the 16-byte tag; decodes cleanly

Why metadata is authenticated, not trusted

The GCM tag protects each block's ciphertext, but the envelope fields sit outside those tags. A recipient should therefore cross-check declared values against observed ones after decryption: the sum of plaintext block lengths must equal originalSize, and the number of decrypted blocks must equal blockCount. Where stronger guarantees are needed, bind metadata into the authenticated data of each block.

Hostile input

A package is untrusted input. Validate lengths before decoding Base64, cap the total allocation, and never use originalName as a path component when writing files server-side.

13 · Reconstruction

Read blocks in their defined order, authenticate and decrypt each with its corresponding nonce and key, then concatenate plaintext bytes. Any authentication failure should abort the operation and report an error; partial output must not be presented as a valid reconstruction.

  1. Parse the package and validate the schema and size limits.
  2. Sort chunks by index and verify they are contiguous.
  3. Import the key and decode each IV to exactly 12 bytes.
  4. Decrypt each block with AES-GCM; the API verifies the tag before returning plaintext.
  5. Append the plaintext to an output buffer in order.
  6. Compare the total length with originalSize before offering the file for download.

Failure behavior

  • Wrong key: the first block fails authentication. Report a key mismatch; do not retry silently with other keys.
  • Tampered ciphertext: the affected block fails; the whole reconstruction is rejected.
  • Missing or duplicated index: structural rejection before any decryption is attempted.
  • Truncated package: JSON parse or length validation fails; nothing is written.

The strictness is the point. An authenticated-encryption scheme that is allowed to "skip a bad block" is no longer authenticated; it has quietly become an unauthenticated one with extra steps.

14 · Private S3

An S3 bucket used as a CloudFront origin should have public access blocked. Bucket policy should grant only the intended distribution origin identity access, with least-privilege actions and resources. This project does not provision or configure an actual bucket.

Baseline expectations

  • Block Public Access enabled at the account and bucket level.
  • No public ACLs; ACLs disabled in favor of bucket policies where possible.
  • Only s3:GetObject granted to the distribution for read-only delivery.
  • Bucket versioning considered for recovery from accidental overwrite.
  • Access logging or CloudTrail data events enabled where appropriate.
  • Default encryption at rest enabled as defense in depth — not as a substitute for client-side encryption.

A conceptual policy shape is shown below. It is illustrative only and must be adapted to the real distribution ARN and account. 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipalReadOnly",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-cloudbox-bucket/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/EXAMPLEID"
        }
      }
    }
  ]
}
Not provisioned

CloudBox ships no bucket, no policy, and no credentials. The snippet exists to make the access model concrete, not to be pasted blindly into an account.

Why public-read is the wrong shortcut

A public-read bucket makes the object reachable by anyone with the URL. If the package is properly encrypted the plaintext may still be protected, but you have lost the ability to revoke access, invalidate links, and audit retrieval. Access control and encryption are complementary, not interchangeable.

15 · CloudFront

CloudFront distributes static objects through edge locations and can cache content near viewers. Cache behavior, object invalidation, TLS configuration, and origin access policy must be selected and tested for the deployment. No real distribution domain is supplied here.

Configuration topics to decide
Topic What to decide Risk if skipped
Cache behavior Path patterns, allowed methods, compression Stale HTML or unnecessary origin fetches
TTLs Minimum, default, and maximum cache duration Outdated content or excessive invalidation cost
Invalidation When and how to purge changed objects Users see the previous release
TLS Minimum protocol version, certificate source Weak transport or browser warnings
Origin access OAC association and signing behavior Access denied errors or an over-exposed origin
Error responses Custom error pages for 403 and 404 Confusing failures during debugging

For a documentation site, HTML should generally use short TTLs while hashed static assets can be cached aggressively. Encrypted packages behave like immutable content: because each run produces a new ciphertext, a new key, and a new object name, long caching is usually safe.

Edge caching is not authorization

A cached object can be served without contacting the origin, so any decision that must be re-evaluated per request belongs at a layer that actually runs per request — signed URLs, signed cookies, or an authorizing compute layer. CloudBox does not implement either; it documents the gap.

16 · Origin Access Control

OAC lets CloudFront sign requests to an S3 origin. The origin bucket policy must refer to the correct distribution and service principal. Misconfigured policies may produce access denied responses or expose objects more broadly than intended.

How the signed request works

  1. A viewer requests an object from the distribution domain.
  2. CloudFront checks its cache for a valid entry.
  3. On a miss, CloudFront signs the origin request using its origin access control configuration.
  4. S3 evaluates the bucket policy, including the AWS:SourceArn condition, and returns the object if the request matches.
  5. CloudFront caches and returns the response to the viewer.
# OAC configuration checklist (conceptual)
1. Create an Origin Access Control with "Sign requests" enabled.
2. Attach the OAC to the S3 origin in the distribution.
3. Deny direct public access to the bucket.
4. Grant s3:GetObject only to the CloudFront service principal.
5. Restrict the grant with AWS:SourceArn = this distribution.
6. Verify with: distribution URL returns 200, bucket URL returns 403.

Common misconfigurations

  • Policy references the wrong distribution ARN: every origin request returns 403 while the bucket looks correct.
  • Principal is a wildcard: the origin is effectively public through any CloudFront distribution.
  • Both legacy OAI and OAC attached: confusing diagnostics and inconsistent signing behavior.
  • Missing s3:GetObject: policy looks restrictive but does not allow the read it must allow.
  • Block Public Access disabled "to make it work": the real problem was the policy condition, not public access.
Verification habit

After any origin change, test both paths: the distribution URL should succeed, and a direct request to the bucket endpoint should fail. If both succeed, the origin is not private.

17 · HTTPS

Serve the website and object downloads over HTTPS. TLS protects data in transit between endpoints; it does not provide file-level encryption after a trusted endpoint has received plaintext. Web Crypto is available only in secure browser contexts, typically HTTPS or localhost.

  • Transport protection: encrypts the channel between viewer and edge, and between edge and origin where supported.
  • Integrity in transit: detects modification during transfer, complementing the per-block GCM tag.
  • Secure-context gate: without HTTPS (or localhost), crypto.subtle is typically unavailable.

Practical configuration notes

  • Redirect HTTP to HTTPS rather than serving both.
  • Disable obsolete protocol versions; prefer TLS 1.2 and above.
  • Consider HSTS once the domain is fully HTTPS-only.
  • Ensure all subresources are HTTPS to avoid mixed-content blocking.
  • Do not place keys or sensitive tokens in query strings; URLs leak through logs, referrers, and caches.
Frequent misconception

End-to-end encryption means the service in the middle cannot read the content. HTTPS to a service that decrypts and stores plaintext is not end-to-end encryption — it is encrypted transport plus whatever the service does next.

18 · Upload path

In the educational flow, a user selects a local file and the client prepares encrypted output. There is no authenticated upload API in this prototype. A production upload design would need identity, authorization, safe key handling, request limits, logging, abuse controls, and a well-defined destination policy. Do not put permanent AWS credentials in frontend code.

Demonstrated flow

  1. The user chooses a file with the file picker.
  2. The client reads it in blocks and computes the block plan.
  3. Each block is encrypted with a fresh IV.
  4. A versioned JSON package is assembled in memory.
  5. The package is offered as a download; the key is offered separately.

What a production upload would add

Identity

An authenticated principal so that uploads can be attributed, limited, and revoked.

Authorization

Short-lived presigned URLs or a scoped upload endpoint instead of long-lived credentials in the browser.

Abuse controls

Size caps, rate limits, content-type checks, and monitoring for anomalous volume.

Key handling

A documented story for wrapping, storing, and recovering keys that never travels with the package.

The most common mistake in this area is embedding permanent AWS access keys in frontend JavaScript. Anything shipped to a browser is public, regardless of minification or obfuscation. Presigned URLs exist precisely to avoid that.

19 · Download path

A configured CloudFront URL can deliver an encrypted package over HTTPS. The recipient must separately possess the correct key and package. The client then validates metadata, authenticates and decrypts each block, and reconstructs the file locally.

  1. Request the package from the distribution domain over HTTPS.
  2. Receive the cached or origin-served JSON envelope.
  3. Validate the schema, version, and declared sizes.
  4. Obtain the key through a separate trusted channel.
  5. Decrypt and authenticate every block in index order.
  6. Concatenate plaintext, verify total length, and offer the file.
Failure modes on the download path
Symptom Likely cause Next check
403 from the distribution Origin access misconfiguration OAC association and bucket policy condition
Older package than expected Edge cache still serving previous object TTL settings or an explicit invalidation
CORS error in the browser Missing or narrow CORS configuration Allowed origins, methods, and headers
Authentication tag mismatch Wrong key or altered ciphertext Key pairing and package integrity
Partial or corrupt output Missing chunk or bad index order Chunk count and index continuity

Because the package is static, the download path has no server-side authorization step in this prototype. That is acceptable for a demo of ciphertext delivery and unacceptable for anything that requires per-user access decisions.

20 · Troubleshooting

  • Crypto API unavailable: use localhost or a deployed HTTPS origin.
  • Authentication tag error: check key, nonce, package integrity, and block association; do not bypass verification.
  • Origin access denied: review distribution origin, OAC association, and S3 bucket policy.
  • Browser memory pressure: use smaller blocks and avoid large concurrent operations.
  • Download fails: verify URL, HTTPS, CORS behavior, and CloudFront cache configuration.
Extended troubleshooting map
Observation Where to look Safe fix
Theme does not persist Local storage access, script errors Re-enable storage or check console for blocked scripts
Mobile menu does not open Module load failure, missing data attributes Confirm app.js loads without errors
Copy buttons do nothing Clipboard permissions in the browser Grant permission or copy manually
Package too large to open File size versus available memory Reduce file size or block size
Slow processing on mobile Per-block crypto cost Smaller blocks and one operation at a time
Inconsistent results after redeploy CDN caching of HTML Invalidate HTML paths or shorten TTLs
Do not "fix" crypto errors

Suppressing an authentication failure by falling back to unauthenticated decryption or by ignoring failed blocks converts a detectable problem into silent data corruption. Fix the key or the package instead.

21 · Security notes

Keep the encryption key separate from the encrypted package and out of public repositories, public websites, and query strings. Treat browser memory, shared devices, extensions, and endpoint compromise as part of the threat model. Never claim that HTTPS alone is end-to-end encryption.

Threat model at a glance

Selected threats and prototype coverage
Threat Covered? Notes
Object store operator reads files Partially Only ciphertext is stored, but key management is out of scope
Tampering with stored ciphertext Yes GCM tag fails authentication per block
Interception in transit Yes HTTPS required for hosted delivery
Compromised browser or extension No Endpoint holds plaintext and key during the operation
Malicious package from an untrusted source Partially Schema validation limits damage; DoS via size is still possible
Credential leakage in frontend code N/A No cloud credentials are present in the prototype
Key loss by the user No No recovery or escrow mechanism exists

Key handling do and do-not

  • Do keep the key out of the package, the page source, and the URL.
  • Do prefer non-extractable keys where the workflow permits.
  • Do deliver keys through a channel separate from the ciphertext.
  • Do not commit sample keys to a repository, even as placeholders.
  • Do not log key material or decrypted metadata.
  • Do not reuse an IV with the same key under any circumstance.

Finally, be careful with language. Terms like "secure", "private", and "encrypted" carry assumptions. The documentation uses them narrowly: encrypted means transformed with AES-GCM; private means not publicly retrievable; secure is avoided unless a specific property is named.

23 · Future work

Potential work includes a reviewed package schema, streaming encryption and decryption, interoperable test vectors, a threat-model review, signed upload authorization, identity integration, retention policy, cloud deployment automation, and a reproducible security test suite.

Grouped roadmap

Format & crypto

Freeze a versioned schema, add authenticated metadata, publish test vectors, and evaluate streaming AES-GCM with bounded memory.

Identity & access

Introduce a login flow, per-user authorization, and short-lived presigned upload/download URLs.

Assurance

Grow the automated test suite, add cross-browser checks, and commission an independent review of the threat model.

Near-term, high-value items

  1. Write the package schema down as a versioned specification with examples.
  2. Add negative tests for tampered ciphertext and reordered chunks.
  3. Replace in-memory assembly with streaming where the platform allows.
  4. Add a clear recovery warning to the key download step.
  5. Document a deployment checklist that separates "described" from "configured".

24 · Conclusion

CloudBox presents a useful conceptual chain: segmentation makes file processing manageable, authenticated encryption protects content, private object storage limits origin exposure, and CloudFront accelerates delivery. Secure implementation depends on the details at each boundary and on being honest about what is not deployed.

If there is a single takeaway, it is that these mechanisms solve different problems and fail in different ways. Segmentation is a memory and granularity decision. AES-GCM is a confidentiality and integrity decision. A private bucket with Origin Access Control is an access decision. HTTPS is a transport decision. None of them substitutes for another, and a design that treats them as interchangeable will look secure while leaving an obvious gap.

The prototype is deliberately unfinished at the points where real systems get hard: identity, key lifecycle, streaming, and operational assurance. Naming those gaps is part of the educational goal, and the recommended next step for anyone extending this work is to close them one at a time, with tests and a written rationale for each decision.
