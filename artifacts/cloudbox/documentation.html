01 · Abstract

CloudBox is an educational secure-file-storage and content-delivery prototype. It explains client-side file segmentation, AES-256-GCM authenticated encryption, private Amazon S3 storage, and CloudFront delivery as connected but distinct concerns. The project is a learning artifact, not a managed storage product or audited security system.

02 · Introduction

Large-file workflows involve transport, storage, confidentiality, integrity, and retrieval. CloudBox makes those concepts visible through a static educational site and a browser-oriented file workflow. It separates the trust decisions made by the client from the access rules of a cloud origin.

03 · Problem statement

Users often confuse HTTPS, private buckets, and encryption at rest with end-to-end file confidentiality. They are not interchangeable. The project demonstrates where file bytes are transformed and where origin access is controlled, while making missing services and assumptions explicit.

04 · Objectives

  • Demonstrate block-based file processing with a configurable block size.
  • Explain AES-GCM confidentiality and tamper detection at a high level.
  • Show private S3 and CloudFront OAC as a static content delivery pattern.
  • Provide a transparent test ledger and useful operational documentation.

05 · Scope

Included: static project pages, architecture diagrams, documentation, browser workflow interface, and a manually maintained test ledger. Excluded: account management, authenticated upload API, credential management, production key escrow, cloud provisioning, and security certification.

06 · Technology stack

The presentation layer uses semantic HTML, CSS, and vanilla JavaScript. Vite is a development and build tool that emits a static multi-page distribution. The architecture discussion references browser cryptography concepts, Amazon S3, CloudFront, Origin Access Control, and HTTPS.

No backend or database is required for this educational website. Test annotations can be saved locally in the visitor's browser.

07 · Hardware and software requirements

Hardware

  • A computer or phone with enough free memory for browser-based file processing; large files need substantially more memory than their source size.
  • Internet access is needed only for hosted pages or configured CloudFront downloads.

Runtime software

  • A modern browser with JavaScript and Web Crypto enabled.
  • A secure context such as HTTPS or localhost for cryptographic APIs.
  • Local file access granted by the user through a file picker.

Build software

Node.js and pnpm are needed only to develop or build the static pages.

09 · Local setup

From the workspace root in Replit, run the artifact workflow or use the command below. In Windows PowerShell, open the project workspace folder first and run the same pnpm command. To deploy the static site, build it and upload the contents of the output directory.

# Replit or Windows PowerShell, from the workspace root
pnpm --filter @workspace/cloudbox run dev

# Build static files for S3 / CloudFront
pnpm --filter @workspace/cloudbox run build
# output: artifacts/cloudbox/dist/

Web Crypto is restricted outside secure contexts in many browsers. Use HTTPS in Replit or localhost for local development rather than opening an HTML file directly from disk. No database setup is required.

10 · Segmentation

The source file is treated as a byte sequence and split into ordered ranges. A block size of 1 MiB is a practical educational default, not a universally optimal setting. The final block may be smaller than the configured size.

For a file of size S bytes and block size B, estimated block count is ceil(S / B). Empty files need explicit format handling.

11 · Cryptography

CloudBox uses an extractable 256-bit AES key for the demonstration, with AES-GCM and a 128-bit authentication tag. It generates a fresh random 12-byte IV for each block. AES-GCM combines encryption with an authentication tag that detects ciphertext changes; a robust design must never reuse an IV with the same key and must reject any block that fails authentication.

Cryptographic APIs should use the browser's Web Crypto implementation rather than custom algorithms. This educational prototype does not claim independent cryptographic review.

12 · Package format

The versioned package records the original file name and type, file size, block size, count, and indexed chunks. Each chunk carries a Base64 IV and authenticated ciphertext. The raw key is kept out of the package and downloaded separately.

{
  "format": "cloudbox-encrypted-package",
  "version": 1,
  "algorithm": "AES-256-GCM",
  "originalName": "example.bin",
  "originalType": "application/octet-stream",
  "originalSize": 42,
  "blockSize": 1048576,
  "blockCount": 1,
  "chunks": [
    { "index": 0, "iv": "Base64-encoded 12-byte IV", "ciphertext": "Base64-encoded ciphertext and GCM tag" }
  ]
}

Validate package sizes and schema before allocating memory. Do not trust a supplied filename as a filesystem path. The example values and payload strings are illustrative, not an actual encrypted package.

13 · Reconstruction

Read blocks in their defined order, authenticate and decrypt each with its corresponding nonce and key, then concatenate plaintext bytes. Any authentication failure should abort the operation and report an error; partial output must not be presented as a valid reconstruction.

14 · Private S3

An S3 bucket used as a CloudFront origin should have public access blocked. Bucket policy should grant only the intended distribution origin identity access, with least-privilege actions and resources. This project does not provision or configure an actual bucket.

15 · CloudFront

CloudFront distributes static objects through edge locations and can cache content near viewers. Cache behavior, object invalidation, TLS configuration, and origin access policy must be selected and tested for the deployment. No real distribution domain is supplied here.

16 · Origin Access Control

OAC lets CloudFront sign requests to an S3 origin. The origin bucket policy must refer to the correct distribution and service principal. Misconfigured policies may produce access denied responses or expose objects more broadly than intended.

17 · HTTPS

Serve the website and object downloads over HTTPS. TLS protects data in transit between endpoints; it does not provide file-level encryption after a trusted endpoint has received plaintext. Web Crypto is available only in secure browser contexts, typically HTTPS or localhost.

18 · Upload path

In the educational flow, a user selects a local file and the client prepares encrypted output. There is no authenticated upload API in this prototype. A production upload design would need identity, authorization, safe key handling, request limits, logging, abuse controls, and a well-defined destination policy. Do not put permanent AWS credentials in frontend code.

19 · Download path

A configured CloudFront URL can deliver an encrypted package over HTTPS. The recipient must separately possess the correct key and package. The client then validates metadata, authenticates and decrypts each block, and reconstructs the file locally.

20 · Troubleshooting

  • Crypto API unavailable: use localhost or a deployed HTTPS origin.
  • Authentication tag error: check key, nonce, package integrity, and block association; do not bypass verification.
  • Origin access denied: review distribution origin, OAC association, and S3 bucket policy.
  • Browser memory pressure: use smaller blocks and avoid large concurrent operations.
  • Download fails: verify URL, HTTPS, CORS behavior, and CloudFront cache configuration.

21 · Security notes

Keep the encryption key separate from the encrypted package and out of public repositories, public websites, and query strings. Treat browser memory, shared devices, extensions, and endpoint compromise as part of the threat model. Never claim that HTTPS alone is end-to-end encryption.

22 · Limitations

  • No user authentication, access-control service, or upload API.
  • No managed key recovery, revocation, rotation, or sharing protocol.
  • Browser memory and available storage constrain file size.
  • No automated AWS provisioning or live AWS configuration is bundled.
  • Educational prototype only; no penetration test or formal audit is claimed.

23 · Future work

Potential work includes a reviewed package schema, streaming encryption and decryption, interoperable test vectors, a threat-model review, signed upload authorization, identity integration, retention policy, cloud deployment automation, and a reproducible security test suite.

24 · Conclusion

CloudBox presents a useful conceptual chain: segmentation makes file processing manageable, authenticated encryption protects content, private object storage limits origin exposure, and CloudFront accelerates delivery. Secure implementation depends on the details at each boundary and on being honest about what is not deployed.
